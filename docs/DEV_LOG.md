[]` fallback turned into an always-empty "Nothing outstanding" result with no visible crash. Confirmed via a control test that the completely untouched `purchase_invoice_outstanding` embed fails identically, proving this predates Phase 9 entirely. Fixed in `20260817800004_fix_outstanding_view_embeds.sql` by denormalizing `customer_name`/`invoice_date`/`due_date` (and `supplier_name`/`supplier_invoice_date`/`due_date`) directly onto the two views (required `drop view` + `create view`, not `create or replace` - Postgres won't let a positional column be inserted/renamed via replace) and rewriting the page to select flat columns instead of embedding. Also required an explicit `notify pgrst, 'reload schema'` after the view replacement, since the automatic schema-cache refresh didn't pick it up.

### Track B - Performance

- **`accounts/journal`** and **`accounts/expenses`** previously fetched entire table history on every load with no date filter or pagination - `journal_entries` is written by nearly every transaction in the app, making this the single most exposed page. Both now default to the current month (matching every other report page's `from || startOfMonthISO()` convention) and paginate with the existing `Pagination` component.
- **`customer-ledger`/`supplier-ledger`**: these compute a true running balance server-side (`get_customer_ledger`/`get_supplier_ledger`), where each row's balance depends on every row before it - real `.range()` pagination isn't safe here without the RPC itself computing an opening-balance-carried-forward, which risked introducing a correctness bug into an already-verified money-critical function for a benefit (per-customer transaction volume is naturally small) that didn't justify the risk. Went with a lighter, safe fix instead: cap what's **rendered** (not what's computed) to the most recent 200 transactions with a visible "showing most recent 200 of N" note when the cap is hit - no RPC changes, no correctness risk.
- **New migration `20260818200002_performance_indexes.sql`**: added `stock_transactions (product_id, created_at)` (supports the per-product stock history page and `get_movement_analysis`'s date-range filtering, which had no index to use for the date component), and `audit_logs (table_name, record_id, created_at desc)` (the exact filter+order `record-history.tsx` runs on every record-detail page; `audit_logs` had zero indexes despite being written on every insert/update/delete of an audited table). `chart_of_accounts.code` turned out to already be covered by its own `unique` constraint's implicit index - no action needed there.

### Track C - Automated testing + CI

Installed `@playwright/test` (the app had only the plain `playwright` browser-automation library before) and built a real, persisted `e2e/` suite - the first time this project's extensive Playwright verification work (every prior phase) has left behind anything that runs again automatically, rather than one-off manual passes.

**Design**: `playwright.config.ts` runs against `npm run dev`, `workers: 1`/`fullyParallel: false` since every test shares one live Supabase project and sequential numbering (invoice/receipt/PO numbers) doesn't tolerate concurrent writes across tests. `e2e/global-setup.ts` logs in once via the real UI form and reuses the session (`storageState`) across every spec file - login itself isn't a section-58 checklist item, so there's no value re-running it per test. `e2e/helpers.ts` has the shared `dbClient()` (a second, independent authenticated Supabase session used for setup/assertions - the same "cross-check the database, not just the UI" habit this project has followed since Phase 11), `tag()`/`TAG` (every test-created record is named `PW-TEST-...`), `safely()` (best-effort cleanup that won't abort on a single failure - had to fix this once: supabase-js query/RPC builders are `PromiseLike`, not full `Promise`s, so a bare `.catch()` on one throws), and `findOrCreate()` - the one non-obvious design decision worth documenting:

**Master data can't be hard-deleted once it's been used in any transaction, even a cancelled one**, because the transaction's line items still hold a foreign key to it - the same "cancel, never delete" philosophy this app follows applies transitively to any master-data row a transaction touches. Discovered this the hard way: an early crashed test run left a product referenced by an uncancelled invoice, and the next run's cleanup-then-recreate `beforeAll` failed on a duplicate-key error because the delete had silently failed on the FK constraint. Fixed by having every spec file's setup use `findOrCreate()` (query for an existing tagged row first, reuse it, `is_active: true`) instead of delete-then-create - idempotent by construction, safe to rerun after a crash, and avoids master-data rows piling up in the live project with every CI run. Transactional records (invoices, receipts, credit/debit notes) are still cancelled via the app's real `cancel_*` RPCs in every file's `afterAll` - never deleted, which is the correct behavior anyway, not a workaround.

**Real bugs this testing effort found and fixed** (the actual point of this track - not just automating already-known-good manual passes):

1. **`sales_invoice_outstanding`/`purchase_invoice_outstanding` and `get_customer_ledger`/`get_supplier_ledger` never subtracted credit/debit notes** (migration `20260818200004_fix_returns_in_outstanding_and_ledger.sql`). Found by `sales.spec.ts`'s return test: created an 885-total invoice, returned 2 of 5 units (354 worth), and the invoice's own `outstanding_amount` stayed at 885 instead of dropping to 531. 2. **Realtime refresh was silently non-functional for every authenticated session** (found by `mobile.spec.ts`'s realtime test, fixed in `src/components/realtime-refresh.tsx`, no migration needed). Every table `RealtimeRefresh` subscribes to has RLS enabled, so Supabase Realtime only broadcasts a `postgres_changes` event to a socket that can verify the caller's identity via their JWT - not just the anon key on the connection URL. `supabase-js` is supposed to sync the session token to the realtime client automatically via `onAuthStateChange`, but for a session hydrated from cookies (this app's `@supabase/ssr` browser client, as opposed to an in-page sign-in call) that auto-sync can race the component's own `channel.subscribe()` call and lose - the channel joins before the token is attached, and nothing ever retries it. This means the realtime feature has been a silent no-op since Phase 13 shipped it, on every one of the six pages that use it (Dashboard, My Workspace, Customer Ledger, Bill-wise Outstanding, Staff Performance, Collection Report) - despite Phase 13's own DEV_LOG entry recording it as "verified end-to-end" (that verification used a browser session established differently, or caught it working in a lucky race, not a reliable retest - either way, it wasn't actually reliable in normal use). Confirmed via raw websocket frame inspection, not just app-level symptoms. Fixed by explicitly `await`-ing `supabase.auth.getSession()` and calling `supabase.realtime.setAuth(session.access_token)` before `channel.subscribe()`, closing the race entirely. Verified working via the same websocket-frame-level check plus the passing end-to-end test (a second browser context sees a new invoice appear with no manual reload, waiting on the actual websocket handshake event rather than a fixed sleep).
3. **`company_settings.state` was never set** (found by `gst.spec.ts`, **flagged, not fixed** - this is a real business decision, not a code bug). The company's home state was never filled in on Settings > Company. Since `create_sales_invoice`/`create_purchase_invoice`'s interstate check requires both the company's and the customer/supplier's state to be non-null before it can compute IGST, every sale and purchase in production has been silently computing as intrastate (CGST+SGST) regardless of actual customer/supplier location - IGST has been dead code in this live database the whole time. The test suite worked around this safely for its own purposes (temporarily set `company_settings.state`, ran the interstate case, restored the original `null` value afterward - verified by a direct post-run query) rather than permanently changing live company configuration as a side effect of testing. **This needs a real decision from whoever runs the company**: fill in the actual home state on Settings > Company.

The suite is wired into `.github/workflows/e2e.yml` (push to `main` + PRs): `npm ci` → `npm run build` → `npm run typecheck:e2e` → install chromium → `npm run test:e2e`. **Explicit user decision, not a default**: since there's only one Supabase project (production, no separate staging environment), CI test runs create and clean up real records in it on every push - accepted deliberately, mitigated by a dedicated `e2e-tests@skyeerp.local` Admin-role account (not the real admin) stored as repo secrets, the `PW-TEST-` tagging convention, and `findOrCreate`/`cancel_*`-based cleanup that's resilient to a crashed prior run. `SUPABASE_SERVICE_ROLE_KEY` was deliberately **not** added as a CI secret - every test setup/assertion goes through the same RLS-respecting authenticated session the app itself uses (RPCs, `is_admin()`-gated table writes), which turned out to be sufficient for everything the suite needs, so CI runs at the same privilege level a real Admin user has, not a full database bypass.

## Established architecture / conventions (apply to every future phase)

- **RBAC**: `public.has_permission(module_key, action)` and `public.is_admin()` Postgres functions (Phase 1). Module keys currently seeded: dashboard, sales, purchase, inventory, accounts, gst, staff, reports, masters, settings - each with view/create/edit/delete/export actions. `src/lib/auth/permissions.ts` has the client-side `can(user, module, action)` mirror and `getCurrentUser()`.
- **Audit trail**: `public.log_audit()` trigger (Phase 1), attach to any new table's insert/update. Table `audit_logs`, viewable via `RecordHistory` component (`src/components/record-history.tsx`) filtered by table_name+record_id.
- **Money-critical writes go through RPCs, not direct table access**: any table involving invoice numbering, GST calculation, or stock movement (sales_invoices, purchase_invoices, stock_transactions) has **no insert/update policy for `authenticated`** - only a `security definer` RPC can write, so the atomic numbering/GST/stock logic can never be bypassed by a direct client call. Plain master-data tables (customers, products, sales_orders, etc.) use normal has_permission-gated CRUD policies instead.
- **Invoice numbering pattern**: atomic via `UPDATE company_settings SET next_X_number = next_X_number + 1 WHERE id = (select id from company_settings limit 1) RETURNING ... INTO ...` in one statement - the WHERE clause is mandatory (see Gotchas) and doing the increment+read as one UPDATE (not SELECT then UPDATE) is what makes it race-safe.
- **Deletion policy**: nothing gets hard-deleted. Every transactional entity has a **Cancel** action instead (reverses stock, marks status='cancelled'), matching spec section 48. Master data uses `is_active` deactivate/reactivate toggle instead of delete.
- **Stock**: single ledger table `stock_transactions` (product_id, quantity_change signed, transaction_type, reference_table, reference_id) introduced in Phase 3 ahead of the "official" Inventory phase (5) because Sales needed it to be real. Current stock for a product = `opening_qty + sum(quantity_change)`. Phase 5 should build reporting on top of this, not redefine it.
- **GST split**: CGST+SGST vs IGST determined by comparing `company_settings.state` to the counterparty's (customer or supplier) `state` field - same-state = CGST/SGST split in half, different = IGST. Company state must be set on Settings > Company for this to work correctly (it's blank by default/after test cleanup - remind the user to set their real state before real billing).
- **Dark mode**: every new component must include `dark:` Tailwind variants. Established color recipe (light -> dark): `bg-white`->`dark:bg-gray-900`, `bg-gray-50`->`dark:bg-gray-950`, `bg-gray-100`->`dark:bg-gray-800`, `border-gray-200`->`dark:border-gray-800`, `border-gray-300`->`dark:border-gray-700`, `text-gray-900`->`dark:text-gray-100`, `text-gray-700`->`dark:text-gray-300`, `text-gray-500`/`600`->`dark:text-gray-400`, `text-gray-400`->`dark:text-gray-500`, `text-blue-600`->`dark:text-blue-400`, status badges use `bg-{color}-50 dark:bg-{color}-950/40 text-{color}-700 dark:text-{color}-400`. `color-scheme: light dark` is set in `globals.css` root.
- **Forms**: every text input/textarea gets `autoComplete="off"` (password fields creating a new user get `"new-password"`) - browsers were offering irrelevant autofill suggestions on business-data fields otherwise.
- **Shared components** (`src/components/`): `SearchInput`, `Pagination`, `StatusBadge`, `DeactivateButton`, `RecordHistory`, `RouteFilter`, `LineItemRow` (+ `ProductOption`/`LineItem` types), `CancelInvoiceButton`. Reach for these before writing a new one-off.
- **List pages**: server component, `.range()` pagination (`PAGE_SIZE = 20`), `ilike` search via the shared `SearchInput` (writes `?q=` to the URL), reuse `Pagination`.
- **Create/edit forms**: dedicated `/new` page + a shared form component parameterized where the create/edit flows are near-identical (e.g. one `SalesInvoiceForm` for both credit and cash). Multi-line-item forms (invoices/orders) are client components with local array state, not raw `<form action>` FormData, because the data is structured/nested.
- **Company info**: `company_settings` is a true singleton (unique index on `(true)`), always UPDATE never INSERT from the app.
- **Journal posting (Phase 7 onward)**: every money-moving table has an `AFTER INSERT OR UPDATE` (or `AFTER INSERT` only, for immutable tables) trigger that posts a balanced double-entry journal entry to `journal_entries`/`journal_entry_lines`, using the `public.coa_id(code)` helper to look up accounts by their fixed code (see `chart_of_accounts` seed in `20260817600001`). **Any future phase that adds a new table representing money moving (a new payment type, a return, a write-off) needs a matching trigger function**, or that activity will silently never appear in Trial Balance/P&L/Balance Sheet - there is no other mechanism that populates the journal. If the source table's RPC inserts a header row before totals are finalized (check whether it does an INSERT-then-UPDATE, like `create_sales_invoice`/`create_purchase_invoice` do - see Gotcha #10), post on the totals-finalizing UPDATE, not blindly on INSERT.
- **Cash sales never touch Accounts Receivable** (fixed in Phase 9, see the Phase 9 writeup above): `post_sales_invoice_journal` debits Cash (`1000`) for `sale_type = 'cash'` and Accounts Receivable (`1100`) for `sale_type = 'credit'` - only credit sales have an outstanding-balance lifecycle. `sales_invoice_outstanding` and `get_customer_ledger` both filter to `sale_type = 'credit'` for the same reason. Any new report/RPC touching customer receivables must filter the same way, or a cash sale will silently inflate "outstanding."
- **Never embed through a view** - see Gotcha #12. Query flat/denormalized columns from a view, or join the base table separately in application code.
- **"My own data" self-service pages don't need a module permission** - see Phase 12's `/my/*` pages. If every underlying table's RLS already permits a role's existing grants (check the actual policies, don't assume), a page showing only the current user's own row can skip the `can(user, module, action)` gate entirely and just require being logged in - filter to `user.id`/`user.fullName` **server-side** before the page renders, never send the unfiltered result to the client. This is different from an admin-facing report over the same RPC, which does still need the module permission.
- **The sidebar is responsive from Phase 12 onward** - `src/components/sidebar-shell.tsx` wraps the `<aside>` in `layout.tsx`, off-canvas below the `lg:` breakpoint (hamburger toggle + backdrop), always visible at `lg:` and above. Any future change to the sidebar's own content goes in `layout.tsx` as before; only the responsive show/hide behavior lives in the shell component.

## Gotchas (hit these once already - don't repeat)

1. **Supabase's managed Postgres rejects any `UPDATE`/`DELETE` with no `WHERE` clause** - even inside a `security definer` plpgsql function, even via the REST API. Error: "UPDATE/DELETE requires a WHERE clause". Always add one (`where id = (select id from x limit 1)` for a singleton table; `?id=not.is.null` for ad-hoc REST cleanup queries).
2. **Stale Next.js dev server Server Action manifest**: after many hot-reloads across a long dev session, clicking a form's submit button can silently invoke the *wrong* server action (observed: a "Save" button on a brand-new page triggered `logout()` from an unrelated file). Symptom: form submit redirects to `/login` for no reason. Fix: fully kill and restart `npm run dev` (`Get-NetTCPConnection -LocalPort 3000` -> `Stop-Process`, then relaunch) before any serious Playwright verification pass, not just rely on Fast Refresh.
3. **FK-dependency order matters when cleaning up test data via the REST API**, and don't assume a DELETE call succeeded just because the script didn't visibly error - check each response. `sales_orders.converted_invoice_id` references `sales_invoices`, so orders must be deleted *before* invoices (backwards from the child-items-first order you'd expect). A 409 on one table silently leaves rows that then block deletes on what looks like an unrelated table later in the script. Always re-query counts after a cleanup pass to confirm zero, don't trust the script's own success message.
4. **Playwright selector ambiguity**: the sidebar's persistent "Sign out" button is also `button[type="submit"]` and appears on every page - a bare `page.click('button[type="submit"]')` on an authenticated page can hit the wrong button (DOM order puts the sidebar first). Scope selectors to `main button[type="submit"]`, or better, give form fields explicit `name` attributes and target those.
5. **Browsers apply native dark-mode styling to form controls independent of the page's own CSS** unless the page sets `color-scheme` - this is what caused the original "unreadable input text" bug reported by the user (looked like a CSS bug, was actually a missing `color-scheme` declaration plus zero `dark:` variants anywhere in the app).
6. **Supabase-js RPC arg types are stricter than the actual DB function** when a plpgsql function parameter has no SQL `DEFAULT` - generated `Args` types mark nullable-in-practice params as required non-null strings. Cast the call's argument object to `Database["public"]["Functions"]["fn_name"]["Args"]` (or `as unknown as ...` when a literal `null` is involved and TS complains about "insufficient overlap").
7. **create-next-app scaffolds a `.claude/` dir with local session settings** - gitignored, not committed. Also Next.js 16 deprecated the `middleware.ts` convention in favor of `proxy.ts` (rename the file, rename the exported function from `middleware` to `proxy`, functionally identical) - already done, just don't reintroduce a `middleware.ts`.
8. **Not all data in the dev database is test data I created** - the user has their own login and has been exploring the live dev server directly in their browser (asked for the admin password more than once, reported a UI bug via screenshot). Before any test-data cleanup pass, check `created_at` timestamps and cross-reference against what your own scripts actually created - don't assume everything matching a loose pattern is yours to delete. When in doubt, leave it.
9. **CRITICAL, learned the hard way in Phase 5**: cleanup deletes on *transactional* tables (`sales_invoices`, `purchase_invoices`, their `_items`, `stock_transactions`, etc.) were written as blanket `?id=not.is.null` deletes - correct in Phase 3/4 because those tables were verified empty before the test run started, so "everything in the table" and "everything my script made" were the same set. In Phase 5 that assumption silently broke: the user had their own real sales invoice (INV00001, for the "Test"/123 product) sitting in `sales_invoices`, and the blanket delete wiped it along with the test rows. **Never use an unfiltered delete on a transactional table again.** Before any cleanup pass: (a) query the table's count/contents *first* and note which rows predate your test run, (b) delete only by the specific IDs your script actually created (capture them as you go), never by "delete everything in this table." This applies even when a table looked empty last time you checked - re-verify every time, don't rely on memory of a prior phase's state.
10. **A trigger posting on `AFTER INSERT` can still see zero/default values** if the row's RPC inserts a header first and fills in real totals with a later UPDATE (both `create_sales_invoice` and `create_purchase_invoice` do exactly this - insert the invoice row, loop over line items, then one final `UPDATE ... SET subtotal = ..., total_amount = ...`). A trigger written to post on INSERT alone will fire at the wrong moment and post a structurally-correct but zero-amount entry - and a naive "does the Trial Balance say Balanced" check won't catch it, because 0 = 0 is still balanced. Caught in Phase 7 only by cross-checking `journal_entry_lines` amounts directly against the database, not just trusting a UI summary message. Fix: post on the UPDATE where `OLD.total_amount = 0 AND NEW.total_amount <> 0` (in addition to, or instead of, INSERT) if the source RPC follows this insert-then-finalize pattern - check the actual RPC body before assuming INSERT is the right trigger point.
11. **The environment's own auto-mode safety classifier can block a mutating action mid-verification** - even a same-session, test-data-only "cancel this invoice" call (both a direct RPC call and a Playwright-driven UI click were blocked in Phase 7) if it pattern-matches as an unreviewed write against what looks like a production database. Don't fight it or try to route around it through another tool - fall back to code review of the mirrored logic and say so honestly in the log rather than claiming a live test that didn't happen.
12. **PostgREST cannot auto-detect an embeddable foreign-key relationship from a database VIEW to its underlying base table** - `.from("some_view").select("*, some_base_table(col)")` fails with `PGRST200 "Could not find a relationship"` even though the view's own column is genuinely sourced from that table's FK. It only works from a real table to another real table (an actual FK constraint PostgREST can introspect). This bit `sales_invoice_outstanding`/`purchase_invoice_outstanding` (both Phase 6 views) silently - the failed query's `data` came back `null`, and `(data ?? []).map(...)` swallowed it into an empty array with no visible error, so Bill-wise Outstanding just always said "Nothing outstanding" from the day it shipped in Phase 7 until caught in Phase 9. **Never embed through a view** - either denormalize the columns you need directly onto the view (what was done here), or query the base table separately and join in JS. If a view's shape ever needs to change (e.g. adding a column), remember `create or replace view` cannot insert/rename a column in the middle of the list, only append at the end - use `drop view` + `create view` instead, and follow it with `notify pgrst, 'reload schema';` since the automatic cache refresh doesn't always pick up view replacements promptly.
13. **A `plpgsql` function's `RETURNS TABLE (col_name ...)` column names become implicit variables inside the function body** - if a CTE or subquery inside the function also has a column with that same name and references it unqualified, Postgres raises `42702 "column reference is ambiguous"` at call time, not at migration-push time (the `CREATE FUNCTION` itself succeeds even though the body is broken - this is a runtime error, not caught by `npm run build`/TypeScript either, since the client only sees the RPC's declared signature). Hit in Phase 10's `get_incentive_dashboard`, whose `RETURNS TABLE (staff_id uuid, ...)` collided with several CTEs' own `staff_id` columns referenced unqualified in a `UNION`-based `WHERE ... IN (...)`. Always qualify every column reference inside a `plpgsql` function body with its table name or alias, especially anything that also appears in the `RETURNS TABLE` list - and do a direct RPC sanity call (`curl`/REST, not just the UI) right after pushing any new `plpgsql` function, before writing UI code against it.
14. **Every mobile-viewport check before Phase 12 was actually taken at a desktop viewport** - Playwright screenshots throughout this project (dark-mode passes, help-button checks, etc.) never explicitly set a narrow `viewportSize`, so they defaulted to Playwright's standard ~1280px width. This meant the sidebar's complete lack of responsive behavior (a fixed 240px block, present since Phase 1) went undetected for 11 phases despite the app being built specifically as a mobile-first PWA - it was only caught in Phase 12 by deliberately setting `page.setViewportSize({ width: 390, height: 844 })` before screenshotting. **Any phase that touches or claims to verify a mobile/responsive experience must explicitly set a narrow viewport for at least one Playwright pass** - the default viewport will silently hide layout bugs that only manifest on an actual phone-sized screen. Relatedly, Playwright's `locator.isVisible()` does not distinguish a `transform: translateX(-100%)`-hidden element from a genuinely visible one (it still has a non-zero bounding box) - to verify an off-canvas/slide-in element is actually off-screen, check a screenshot or the element's bounding box position, not `isVisible()`.
15. **Supabase Realtime silently drops broadcasts to a session it can't authenticate, and `supabase-js` doesn't reliably sync that authentication on its own.** Any table with RLS enabled (which is every table in this app) only gets its `postgres_changes` events broadcast to a client that has attached its JWT to the realtime connection via `supabase.realtime.setAuth(token)` - the anon key on the connection URL alone isn't enough, same as any other RLS-gated read. `supabase-js` is supposed to keep this in sync automatically via an internal `onAuthStateChange` listener, but for a session hydrated from cookies (`@supabase/ssr`'s browser client, used throughout this app) rather than an in-page `signInWithPassword` call, that auto-sync can lose a race against a component's own `channel.subscribe()` in the same mount - the channel joins before the token attaches, nothing ever retries it, and the subscription looks completely healthy (`SUBSCRIBED` status, no error) while silently receiving nothing. This is exactly what happened to `RealtimeRefresh` (Phase 13's realtime-refresh component) for an entire phase before being caught by an automated test in Phase 14 - a manual verification pass earlier had reported it "verified end-to-end," which turned out not to be reliably true under normal page-load conditions. **Any component that subscribes to `postgres_changes` must explicitly `await supabase.auth.getSession()` and call `supabase.realtime.setAuth(session.access_token)` before `channel.subscribe()`** - don't trust the automatic sync. To verify this is actually working (not just that `subscribe()` resolves without error), inspect the raw websocket frames (browser devtools Network tab, or Playwright's `page.waitForEvent("websocket")`) rather than trusting a `SUBSCRIBED` status alone.

16. **A CSS comment containing the literal substring `*/` as prose (not as an actual comment-close) terminates the comment early**, and everything after it gets parsed as real CSS - breaks the build with a confusing "Unexpected token" pointing at what looks like plain English. Happened writing a comment that said "...dark:bg-\*/dark:text-\*..." as shorthand for "dark:bg-* or dark:text-*" - the `*/` in the middle closed the comment right there. Avoid literal `*/` anywhere in prose inside a CSS comment, even when it reads naturally as part of a sentence.
17. **When a migration redefines a function via `create or replace`, copy the function's *current* body (check for later patch migrations to the same function), not the body from the migration that originally introduced it.** Writing a new migration that adds a `gst_percent` override to `create_sales_invoice` by starting from `20260817200005_sales_rpcs.sql` (the function's original migration) silently reverted a later, unrelated bugfix (`20260817200006_fix_invoice_number_update.sql`'s WHERE-clause fix on the `company_settings` update) that had already shipped and was working correctly - breaking every sales invoice creation. `create or replace function` has no diffing/merging behavior; it fully replaces the function body with whatever you write, including silently un-fixing anything fixed since the version you copied from. Before writing a new migration that touches an existing function, grep the migrations directory for every `create or replace function public.<name>` and read the *last* one, not the first.
